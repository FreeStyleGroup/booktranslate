# Как мы работаем

Правила рассчитаны на то, что над проектом одновременно работают несколько
человек и команд: витрина, API, обработка документов. Всё, что ниже, — про
то, чтобы чужая работа не ломалась молча.

## Ветки

`main` — всегда рабочая: с неё собирается продакшен витрины и с неё режутся
релизные теги. Прямых коммитов в неё нет, только через pull request.

Имя ветки — тип и суть, латиницей:

```
feat/document-ingestion      новая возможность
fix/segment-order            исправление
chore/ci-cache               обвязка, зависимости, конфиги
docs/data-model              только документация
```

## Коммиты

Заголовок — на русском, повелительным наклонением, до 72 символов, без
точки в конце. Тело объясняет **почему**, а не пересказывает диф: что было
не так и почему выбран этот способ. Через полгода ценна именно причина.

Один коммит — одно осмысленное изменение. «Всё за день» одним коммитом
невозможно ни просмотреть, ни откатить.

## Pull request

- До ревью PR обязан быть зелёным: линтер, типы, тесты, сборка.
- Описание — по шаблону: что меняется, зачем, как проверяли.
- Меняешь схему базы — в PR обязана быть миграция, накатывающаяся **и**
  откатывающаяся. CI это проверяет отдельным шагом.
- Меняешь публичный ответ API — обнови типы витрины в том же PR, иначе она
  сломается у соседней команды на следующем деплое.
- PR больше ~400 строк осмысленно не читается: дели.

## Код

**Python (apps/api).** `ruff` и `mypy --strict` проходят без замечаний.
Аннотации типов обязательны, включая возвращаемые. Тонкий обработчик →
сервис → репозиторий; SQL не живёт в обработчике. Любая выборка доменных
данных фильтруется по организации — молчаливая утечка чужих данных дороже
любой экономии на слое.

**TypeScript (apps/web).** `eslint` и `tsc --noEmit` без замечаний.
`any`, `@ts-ignore` и `!` для обхода проверок — не применяем: они не
чинят ошибку, а прячут её до продакшена.

**Общее.** Никаких закомментированных кусков «на всякий случай» — для этого
есть история. Никаких «временно захардкожено»: значение либо в настройках,
либо в константе с объяснением, откуда оно взялось. Комментарий объясняет
причину решения, а не пересказывает соседнюю строку.

## Проверки перед PR

```bash
# витрина
cd apps/web && npm run lint && npm run typecheck && npm run build

# API (в контейнере: локальный Python 3.9 этот код не соберёт)
docker compose exec api ruff check .
docker compose exec api ruff format --check .
docker compose exec api mypy app
docker compose exec api pytest
```

## Секреты

В репозитории нет ни ключей, ни паролей, ни строк подключения с ними.
Локальные значения — в `.env` (он в `.gitignore`), пример — в `.env.example`.
Секреты CI — в GitHub Secrets, секреты витрины — в переменных окружения
проекта Vercel.
