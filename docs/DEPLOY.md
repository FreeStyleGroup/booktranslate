# Выкат на сервер

Обе половины — витрина и API — поднимаются на одной машине в докере, рядом
с базой, за одним обратным прокси. Витрина ходит в API по внутренней сети,
снаружи у каждой свой домен.

Так задумано не всегда было: первоначально витрина жила на Vercel. Почему
переехала и как вернуть её туда при необходимости — в конце, раздел
«Витрина на Vercel».

## Что нужно от машины

- Linux с докером и `docker compose` v2. Памяти — 2 ГБ: витрина, API,
  Postgres и прокси вместе занимают около гигабайта в покое, а разбор
  большой книги и перевод идут в одном процессе API и просят ещё столько же.
  1 ГБ — впритык, первый большой документ это покажет;
- два имени, оба A-записью на эту машину: сайт и API. Сайт — тот адрес,
  который набирает посетитель; это может быть и голый домен
  (`booktranslate.ru`), и поддомен (`app.example.ru`). API живёт на
  отдельном имени, обычно `api.<домен>`: разные имена нужны, чтобы прокси
  понимал, кому отдавать запрос, и чтобы API можно было увезти отдельно.
  На голом домене заводится и третья запись — `www.<домен>`: сертификат
  выпускается и на неё, а прокси перенаправляет такой заход на адрес без
  `www` (постоянное, 301). Сертификаты выпускаются автоматически, и к
  моменту запуска все записи должны уже отвечать — иначе прокси будет
  бесконечно пытаться получить сертификат и писать об этом в журнал;
- открытые снаружи 80 и 443. Больше ничего наружу смотреть не должно:
  порты базы, API и витрины в боевом compose не публикуются вовсе.

## Одной командой

Всё, что ниже в этом документе до раздела «Обновление», делает скрипт
`deploy/bootstrap.sh`. Заранее нужны три вещи: тег `v<версия>` в
репозитории (по нему собраны образы), токен GitHub (classic) с правом
`read:packages` и две A-записи на IP сервера.

```bash
# со своей машины
scp deploy/bootstrap.sh root@<IP>:/root/
ssh -t root@<IP> 'sed -i "s/\r$//" bootstrap.sh && bash bootstrap.sh'
```

🔥 `ssh -t` обязателен: скрипт спрашивает ключ модели и токен GitHub
скрытым вводом, а без терминала эхо выключить нельзя — секреты оказались бы
на экране. Без `-t` скрипт останавливается на первом вопросе и говорит об
этом. Секреты не передавайте переменными в строке команды: строка попадает
в историю оболочки.

`sed` перед запуском — страховка от Windows-переносов строк: если файл по
дороге открывали в редакторе, который ставит `\r\n`, bash на такой скрипт
отвечает «bad interpreter». На файле с обычными переносами (а в
репозитории они именно такие) команда ничего не меняет.

Скрипт спросит домены, ключ модели, токен реестра и почту администратора
(или возьмёт их из переменных окружения, если заданы), сгенерирует секреты,
покажет SSH-ключ для Deploy keys и подождёт, пока вы его добавите, поднимет
compose, дождётся `healthy`, проверит оба домена снаружи, заведёт
администратора и сделает пробный вызов модели. Повторный запуск безопасен:
сделанное пропускается, `.env` не перезаписывается.

Вход root и вход по паролю скрипт **не закрывает** — это нельзя делать, не
проверив ключ. После проверки из второго окна, что `ssh deploy@<IP>` пускает:

```bash
ssh -t root@<IP> bash bootstrap.sh harden
```

Шаг пишет свой файл в `/etc/ssh/sshd_config.d/00-booktranslate.conf`, а не
правит `sshd_config`: образы хостингов кладут туда `50-cloud-init.conf` с
`PasswordAuthentication yes`, и у sshd побеждает первое вхождение — правка
основного файла ничего бы не закрыла. Результат проверяется по `sshd -T`,
а не по содержимому файла.

Что скрипт делает по шагам — ниже, если нужно пройти руками или понять,
что именно он настроил.

## С чистого сервера до докера

Ubuntu 24.04 LTS, вход по паролю root — как отдаёт хостинг. Порядок тот
же, что на других серверах компании, чтобы через полгода не разбираться,
почему две машины устроены по-разному.

```bash
ssh root@<IP>

apt update && apt upgrade -y
timedatectl set-timezone Europe/Moscow

# Рабочий пользователь. Root по паролю снаружи закрывается ниже — но
# только после того, как вход по ключу проверен из второго окна.
adduser --gecos "" deploy
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh
cp /root/.ssh/authorized_keys /home/deploy/.ssh/ 2>/dev/null || true
chown -R deploy:deploy /home/deploy/.ssh && chmod 700 /home/deploy/.ssh
```

Если ключа у root не было, положите свой публичный ключ в
`/home/deploy/.ssh/authorized_keys` (права 600). Затем **из второго окна**
`ssh deploy@<IP>` — и только когда он пустил:

```bash
# Свой файл раньше 50-cloud-init.conf: у sshd побеждает первое вхождение.
printf 'PermitRootLogin no\nPasswordAuthentication no\nKbdInteractiveAuthentication no\n' \
    > /etc/ssh/sshd_config.d/00-booktranslate.conf
sshd -t && sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication) '   # оба «no»
systemctl restart ssh

# Наружу — только SSH и веб.
apt install -y ufw fail2ban unattended-upgrades
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp
ufw --force enable
systemctl enable --now fail2ban

# Докер — из репозитория Docker, а не из apt Ubuntu: там старый compose.
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy
```

Дальше всё от `deploy` (перелогиньтесь, чтобы группа `docker` подхватилась):
`docker compose version` должен показать v2.

⚠️ Если `docker pull` зависает на больших слоях при живой сети — это MTU:
на части хостингов (reg.ru точно) интерфейс урезан до 1450, и докер с
умолчанием 1500 теряет крупные пакеты. Лечится
`/etc/docker/daemon.json` → `{"mtu": 1400}` и `systemctl restart docker`.

### Доступ к репозиторию

Репозиторий приватный. Клонировать по SSH ключом сервера, а не токеном в
адресе — токен в URL оседает в `.git/config` навсегда:

```bash
ssh-keygen -t ed25519 -C "booktranslate-server" -N "" -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
```

Публичный ключ — на GitHub: репозиторий → Settings → Deploy keys → Add,
**без** права записи. Проверка: `ssh -T git@github.com` отвечает
приветствием.

## Перед первым выкатом — один раз

### 1. Собрать образы

Образы собирает GitHub Actions по тегу вида `v0.1.0`
(`.github/workflows/release.yml`) — оба, витрины и API, одним тегом. Пока
тега нет, нет и образов: `docker compose pull` ответит «manifest unknown».

```bash
git tag v0.1.0
git push origin v0.1.0
```

Через несколько минут в Actions появится прогон «Release» с двумя
образами. Номер тега — тот, что потом стоит в `.env` (`API_IMAGE`,
`WEB_IMAGE`), без буквы «v».

### 2. Дать серверу доступ к реестру

Репозиторий приватный, и образы в GHCR тоже приватные. Серверу нужен
токен, чтобы их скачать: на GitHub → Settings → Developer settings →
Personal access tokens → **Tokens (classic)** → права только
`read:packages`. Срок — конечный; продление раз в год лучше, чем токен,
который живёт вечно на чужой машине.

```bash
docker login ghcr.io -u <логин GitHub>     # пароль — этот токен
```

Докер запоминает вход в `~/.docker/config.json` — повторять при каждом
выкате не нужно.

## Порядок

```bash
git clone git@github.com:FreeStyleGroup/booktranslate.git && cd booktranslate

cp apps/api/.env.production.example .env
$EDITOR .env          # см. ниже, что заполнить обязательно

docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml logs -f api    # миграции и старт
```

Миграции накатываются при старте контейнера API. Это осознанный выбор для
одной машины: ручной шаг, про который забывают, ломает выкат чаще, чем
автоматический — который ломает. Откат остаётся отдельной командой и
делается руками.

### Первый администратор

Доступ открывает администратор площадки, а самого его открыть некому —
поэтому он заводится из консоли:

```bash
docker compose -f docker-compose.prod.yml exec api \
    python -m app.cli create-superuser --email you@example.ru
```

Пароль команда либо спросит, либо сгенерирует и напечатает один раз.
Дальше всё через `/root` на витрине: заявки, одобрение, приостановка,
заведение пользователей.

Администратор площадки одобряет только заказчиков — организации. Своих
людей заказчик приглашает сам, в разделе «Команда» кабинета: по почте,
одноразовой ссылкой на неделю; приглашённый входит без второго одобрения.

### Сменить администратора площадки

Та же команда на новую почту заводит второго администратора (или
повышает существующую учётную запись):

```bash
docker compose -f docker-compose.prod.yml exec api \
    python -m app.cli create-superuser --email new-admin@example.ru
```

Затем войдите новым и в `/root` приостановите прежнего. Не наоборот:
закрыв доступ единственному администратору, площадку откроет уже только
эта консольная команда. Самому себе доступ закрыть нельзя — это
проверяется.

### Проверить модель, не переводя книгу

```bash
docker compose -f docker-compose.prod.yml exec api python -m app.cli check-provider
```

Команда печатает действующие настройки (ключ — только началом и длиной),
переводит две короткие строки и показывает расход. `--lookup` заодно
проверяет поиск справок — он ходит в интернет и оплачивается отдельно.

Это единственный способ убедиться, что ключ рабочий: конфигурация
проверяется чтением, а просроченный ключ, недоступный шлюз и
переименованная модель — только вызовом.

## Проверка после выката

По порядку, снизу вверх — так первый же отказ показывает слой, а не
симптом на три слоя выше.

```bash
docker compose -f docker-compose.prod.yml ps
```

У `postgres`, `api` и `web` в колонке STATUS должно стоять `(healthy)`.
`api` со статусом `unhealthy` при рабочем сайте — это `ALLOWED_HOSTS` без
`API_DOMAIN`: проверка живости шлёт запрос с этим именем.

```bash
curl -sS https://api.example.ru/health           # {"status":"ok","environment":"production"}
curl -sS https://api.example.ru/health/ready     # {"status":"ready"} — база отвечает
curl -sS -o /dev/null -w '%{http_code}\n' https://app.example.ru/    # 200
```

Дальше — в браузере: `/register` подаёт заявку и показывает «Заявка
отправлена»; `/root` пускает администратора из консольной команды, в
списке видна только что поданная заявка; после одобрения этот человек
входит через `/login` и видит кабинет с настоящими числами (нулями), а не
с пометкой «Демонстрационные данные».

Пометка «Демонстрационные данные» у вошедшего пользователя означает, что
витрина не дозвонилась до API. Первое, что проверить, — `ALLOWED_HOSTS`:
в нём обязано быть имя `api`, по которому витрина ходит внутри докера.

## Обязательные переменные

| Переменная | Почему обязательна |
|---|---|
| `JWT_SECRET` | С ключом из примера подделать токен может любой, кто читал исходники. Приложение с ним не поднимется вне разработки. |
| `POSTGRES_PASSWORD` | База наружу не смотрит, но пароль по умолчанию переживёт первый же чужой контейнер на этой машине. |
| `WEB_DOMAIN`, `API_DOMAIN` | Канонические имена сайта и API. `API_DOMAIN` же использует проверка живости API. |
| `WEB_SITE` | Имена, на которые прокси получает сертификат витрины. Не задано — берётся `WEB_DOMAIN`. На голом домене `bootstrap.sh` пишет сюда `домен, www.домен`, и заход с `www` перенаправляется на адрес без него. |
| `ALLOWED_HOSTS` | Имена, под которыми отвечает API: домен и `api` — имя сервиса для витрины. Закрывает подмену `Host`. |
| `CORS_ORIGINS` | Домен витрины. Браузер сейчас к API не обращается, но звёздочка вне разработки всё равно запрещена. |
| `ANTHROPIC_API_KEY` | Без него перевод не работает. Через шлюз — ключ шлюза. |
| `API_IMAGE`, `WEB_IMAGE` | Теги образов. Без них compose не поднимется — намеренно, чтобы в бой не уехал `latest`. |
| `WEB_URL` | Адрес витрины для ссылок в письмах. Не задан — уведомление приведёт человека на `localhost`. |

Остальное имеет разумные умолчания и описано в
`apps/api/.env.production.example`.

## Фоновый перевод

Книга переводится часами, и держать ради этого открытой вкладку нельзя:
человек ставит её в очередь и уходит. Работу делает отдельный контейнер
`worker` — тот же образ, что у API, другая команда.

Отдельным контейнером, а не задачей внутри API, по одной причине: выкат
новой версии API не должен обрывать перевод на середине. При остановке
докер шлёт SIGTERM, рабочий дописывает пачку и возвращает задание в
очередь — на это ему даётся 30 секунд.

Его видно там же, где остальные:

```bash
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs -f worker
```

⚠️ Миграции накатывает только API. Рабочий их не трогает намеренно: два
процесса, накатывающие схему при старте, — это гонка на схеме базы.

Рабочих можно поднять несколько (`--scale worker=2`): задание достанется
одному, за это отвечает `FOR UPDATE SKIP LOCKED` в очереди. Смысл в этом
появится тогда, когда книги начнут ждать друг друга, и не раньше.

## Уведомления о готовности

Когда книга переведена, приходит письмо. Ящик — площадки, а не заказчика:
письмо с чужого адреса не пройдёт проверку подлинности отправителя и
уедет в спам.

| Переменная | Значение |
|---|---|
| `SMTP_HOST` | Почтовый сервер. Пусто — письма не уходят, и кабинет говорит об этом прямо. |
| `SMTP_PORT` | `465` — защищённое соединение сразу, `587` — с переходом по STARTTLS. Порт 25 не годится: хостинги закрывают его наружу. |
| `SMTP_USER`, `SMTP_PASSWORD` | Учётные данные ящика. |
| `SMTP_FROM` | Обратный адрес, например `no-reply@booktranslate.ru`. |
| `SMTP_FROM_NAME` | Имя отправителя, которое видит человек. |

Проверить, что почта уходит, можно не переводя книгу целиком: поставьте в
очередь короткий файл и посмотрите журнал рабочего — там будет либо
«письмо отправлено», либо причина отказа почтового сервера целиком.

⚠️ Телеграм пока не работает: бот площадки ещё не сделан. Ник в настройках
пространства сохраняется и заработает сам, когда бот появится. Заранее
известно и другое: с российского хостинга `api.telegram.org` недоступен —
соединение отваливается по таймауту при живой сети, — поэтому боту
понадобится свой узел за границей.

## Через шлюз (AITunnel)

Прямой доступ к Anthropic из России требует обходных путей, поэтому
поддержан совместимый шлюз: тот же протокол `/v1/messages`, оплата в
рублях.

```bash
TRANSLATION_PROVIDER=claude                     # без этого работает заглушка
ANTHROPIC_BASE_URL=https://api.aitunnel.ru     # без «/v1»: путь добавит клиент
ANTHROPIC_API_KEY=sk-aitunnel-…
ANTHROPIC_MODEL=claude-opus-5                   # умолчание площадки
```

`ANTHROPIC_MODEL` — умолчание для пространств, которые ничего не
выбирали. Само пространство выбирает модель в «Настройках» из каталога
(`app/services/models.py`: Opus 5, Sonnet 5, Haiku 4.5) — с ценой из
прейскуранта. Умолчание площадки в списке всегда, даже если у шлюза оно
называется по-своему. После смены переменных контейнеры API и рабочего
перезапускаются: настройки читаются при старте.

Что при этом меняется:

- ключ уходит заголовком `Authorization: Bearer`, а не `x-api-key` —
  приложение делает это само по наличию `ANTHROPIC_BASE_URL`;
- запасная модель на случай отказа по правилам безопасности выключается.
  У шлюза для неё своя форма запроса, и анthropic'овскую он отвергает
  целиком: на AITunnel это `400` с текстом «поле fallbacks должно быть
  массивом объектов». Оставленная включённой, она валила бы каждую пачку.

**Что через шлюз работает** (проверено на AITunnel 08.09.2026,
`claude-opus-5`): перевод со структурированным ответом по схеме, кэш
системного сообщения (`cache_read_input_tokens` приходит), счётчики
расхода, поиск справок с веб-поиском и цитатами. То есть весь конвейер, а
не только простой запрос.

**Про деньги.** Имена моделей у AITunnel совпадают с анthropic'овскими
(`claude-opus-5`, `claude-sonnet-5`, …), поэтому оценка стоимости
выводится — но она считается по прейскуранту **Anthropic в долларах**
(`app/services/pricing.py`), а счёт приходит от шлюза в рублях и со своей
наценкой. Число годится, чтобы понять порядок и сравнить книги между
собой; сверять с выставленным счётом им нельзя.

Проверять после смены ключа или модели — `check-provider`: он делает
настоящий вызов, а конфигурацию можно прочитать и с просроченным ключом.

## Обновление

```bash
git tag v0.2.0 && git push origin v0.2.0        # собрать образы
# дождаться прогона Release в Actions

$EDITOR .env                                    # новый тег в API_IMAGE и WEB_IMAGE
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
```

Тег версии, а не `latest`: по нему видно, что именно работает, и откат
сводится к предыдущему тегу в `.env` и повторному `up -d`. Образы
собираются один раз по тегу и дальше только продвигаются — пересборка
«того же» кода перед выкатом означала бы, что в бой уезжает не то, что
проверяли.

Витрина и API обновляются парой: у них один тег, и разъехавшиеся половины
однажды перестанут понимать друг друга — публичный ответ API меняется в
том же PR, что и типы витрины (`CONTRIBUTING.md`).

## Резервное копирование

Ценного два: база и каталог исходных файлов.

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
    pg_dump -U booktranslate booktranslate | gzip > db-$(date +%F).sql.gz

docker run --rm -v booktranslate_api_storage:/data -v "$PWD":/backup alpine \
    tar czf /backup/storage-$(date +%F).tar.gz -C /data .
```

Проверять восстановлением, а не наличием файла: непроверенная копия — это
не копия.

## Витрина на Vercel

Витрина умеет жить и отдельно — на Vercel, как было изначально. Это
годится для превью веток и показа заказчику до слияния; для боевой работы
у варианта два изъяна, из-за которых основным стал один сервер.

**Ограничитель частоты видит Vercel, а не посетителя.** Витрина ходит в
API сама, и с Vercel все её запросы приходят с адресов Vercel. Адрес
посетителя витрина передаёт заголовком, но прокси перед API отбрасывает
его как пришедший от недоверенного источника — а доверять всем адресам
Vercel нельзя, они общие и меняются. В итоге строгая мера на `/auth/*`
(десять запросов в минуту) действует на всех пользователей вместе: десятый
вход за минуту получит отказ, чей бы он ни был. На одной машине витрина
стоит в доверенной сети, и адрес посетителя доходит до API.

**Vercel закрывает деплои своей авторизацией.** Посторонний получает
редирект на `vercel.com/sso-api`, а не страницу; снимается это в Project
Settings → Deployment Protection → Vercel Authentication → Disabled — и
про это забывают при каждом новом проекте.

Если всё же нужно: Root Directory проекта — `apps/web`; переменные
окружения — `NEXT_PUBLIC_API_URL` и `API_URL`, обе равны публичному адресу
API (`https://api.example.ru`); в `.env` на сервере `CORS_ORIGINS` и
`ALLOWED_HOSTS` остаются как есть — витрина с Vercel ходит по публичному
домену. Сервис `web` из боевого compose при этом можно не поднимать.

## Что осталось незакрытым

Честный список, чтобы это выяснилось здесь, а не на боевой машине.

- **Боевой compose ни разу не поднимался на сервере.** Оба образа
  (API и витрина) собраны локально 11.09.2026 из тех же Dockerfile, compose
  и Caddyfile проверены на разбор — но первый `up -d` на сервере всё равно
  станет первым настоящим прогоном; проверка выше написана под него.
- **Конвейера в кабинете нет.** Проекты, загрузка, разбор, термины,
  перевод, очередь замечаний и выгрузка — всё это работает только через
  API (`/docs` вне разработки выключен). В кабинете — обзор и заглушки
  разделов. До появления интерфейса продукт для заказчика — это витрина,
  заявка на доступ и работа через API по договорённости.
- **Перевод идёт порциями, но по-прежнему в запросе.** Один вызов
  переводит `limit` сегментов и отвечает, сколько осталось; клиент зовёт
  до нуля. Правильное решение — фоновая задача с опросом, и она не
  сделана.
- **Учёта денег по организациям нет.** Токены считаются, потолок расхода
  не принуждается: превышение видно в отчёте, но не останавливает работу.
- **Писем нет.** О решении по заявке система не сообщает — администратор
  говорит человеку сам. Подтверждения почты при заявке тоже нет:
  администратор одобряет по почте и названию организации, как их ввёл
  заявитель, — проверять, что почта настоящая, приходится ему.
- **Сменить пароль пользователь не может.** Выданный администратором
  пароль остаётся известен администратору; восстановления по почте нет.
- **Ограничитель частоты живёт в памяти процесса** и считает по адресу.
  На одной машине с одним процессом API этого достаточно; при нескольких
  рабочих процессах мера станет мягче ровно во столько раз, сколько их
  запущено, а клиент с IPv6-подсетью обходит её сменой адреса.
- **Журналирование не заведено.** Разбирать инцидент будет не по чему,
  кроме журнала прокси.
- **Starlette 0.48 в поставке** — у него есть опубликованные уязвимости
  (PYSEC-2026-249 и соседние, все — отказ в обслуживании при разборе
  форм). Разбор multipart обновлён до безопасной версии, потолок тела
  стоит на прокси; переход на FastAPI со Starlette 1.3+ — отдельный шаг с
  прогоном всех тестов.
