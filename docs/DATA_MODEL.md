# Модель данных

Схема ядра: кому принадлежат данные, из чего состоит работа и где живёт
качество перевода. Реализация — `apps/api/app/models/`, первая миграция —
`apps/api/alembic/versions/`.

```
Organization ──< Membership >── User
     │
     └──< Project ──< Document ──< Segment
```

## Организация — корень всего

`Organization` владеет каждой доменной записью. Колонка `organization_id`
обязательна, снабжена внешним ключом и индексом, добавляется через
`TenantMixin`. Запись без владельца — это запись, которая рано или поздно
покажется не тому клиенту.

Удаление организации уносит её данные каскадом: после ухода клиента в базе
не должно оставаться осиротевших строк с его текстами.

## Пользователь и участие

`User` живёт отдельно от организации, а связь вынесена в `Membership` с
ролью. Причина простая: один человек работает сразу в нескольких
организациях — штатный переводчик у себя и подрядчик у заказчика, — и роли
у него там разные. Пара «организация + пользователь» уникальна: два участия
означали бы две роли одновременно и непредсказуемые права.

Роли: владелец, администратор, менеджер, переводчик, редактор, наблюдатель.
Наблюдатель нужен для заказчика перевода — ему видно состояние работы, но
не даётся правка.

## Проект

`Project` — языковая пара плюс общая терминология. Руководство приходит
томами и правками: том — это документ, проект — весь комплект. Единство
терминов держится на уровне проекта, иначе третий том переведён иначе, чем
первый.

Языки — строки по BCP 47 (`en`, `ru`, `de-CH`), не перечисление: добавление
языковой пары не должно требовать миграции базы.

Короткое имя уникально внутри организации, а не глобально: два разных
клиента вправе назвать проект одинаково.

## Документ

`Document` — один загруженный файл со своим состоянием: принят, разбирается,
разобран, переводится, на проверке, готов, ошибка.

Статус хранится колонкой, а не вычисляется по сегментам. Пересчитывать его
на каждый запрос списка из тысячи документов дорого, а состояние «загружен,
но ещё не разобран» по сегментам не определить вовсе — их ещё нет.

`storage_key` — строка, а не путь на диске: сегодня файлы лежат в локальном
каталоге, завтра в объектном хранилище, и модель об этом знать не должна.

`content_hash` отвечает на вопрос «этот файл уже переводили?» — повторная
загрузка того же тома не должна стоить второй раз.

## Сегмент — единица перевода и проверки

Документ хранится сегментами, а не сплошным текстом. Только так можно
показать редактору, что именно проверено, подставить повтор из памяти
переводов и сказать, в каком месте разошлись числа.

У сегмента есть тип: абзац, заголовок, пункт списка, ячейка таблицы,
подпись, предупреждение, код. Переводятся они по-разному: у заголовка свои
требования к краткости, у предупреждения цена ошибки выше всего, код не
переводится вовсе. Тип известен после разбора исходника и влияет и на
промпт, и на строгость проверок.

Статус сегмента отвечает на вопрос «кому верить»: новый, машинный перевод,
подстановка из памяти, правка человека, принято редактором, помечено
проверкой.

Три поля хранят разнородное и потому сделаны JSONB:

- `source_location` — где сегмент стоял в исходнике. У PDF это страница и
  координаты, у DOCX — путь в разметке, у XLIFF — идентификатор единицы.
  Отдельные колонки под каждый формат были бы полем пустот.
- `quality` — результат проверок: расхождение чисел, нарушение глоссария,
  протечка исходного языка, длина. Проверки будут добавляться, и каждая
  новая не должна требовать миграции.
- `quality_score` — свёрнутая оценка отдельной колонкой с индексом, чтобы
  «покажи худшие сто сегментов» был обычным запросом с сортировкой, а не
  разбором JSON по всей таблице.

`translation_source` хранит, откуда взялся перевод — имя модели или
`memory`. Через полгода это единственный способ ответить, какой моделью
переведён конкретный том.

Пара «документ + позиция» уникальна: по позиции сегменты показываются и на
неё ссылаются правки.

## Общие соглашения

**Первичный ключ — UUID**, значение генерируется приложением. Идентификаторы
уезжают в адреса и внешние системы: последовательный номер выдал бы объём
базы и позволил перебирать чужие записи. Генерация на стороне приложения
даёт объекту `id` до вставки, и его можно связывать с другими до похода в
базу.

**`created_at` / `updated_at`** есть у каждой сущности, значения ставит
сервер базы — время приложения на нескольких машинах расходится.

**Имена ограничений заданы явно** соглашением в `app/db/base.py`. Без него
Postgres придумывает имена сам, а следующая миграция не находит нужное
ограничение по имени, и откат превращается в ручную работу с боевой базой.

## Чего здесь пока нет

Память переводов, глоссарий проекта, задания на перевод и журнал правок
сегмента. Всё это ложится поверх текущей схемы без её перестройки — но
проектируется отдельно, вместе с обработкой документов.
