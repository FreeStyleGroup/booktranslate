# Сборка и выкат

Устройство рассчитано на несколько команд, работающих параллельно: правка
витрины не должна ждать тестов бэкенда, а выкат одной части — блокировать
другую.

## Что где живёт

| Часть | Где собирается | Где работает |
|---|---|---|
| Витрина `apps/web` | GitHub Actions → образ в GHCR | свой сервер (Docker), рядом с API |
| API `apps/api` | GitHub Actions → образ в GHCR | свой сервер (Docker) |
| База | — | Postgres рядом с API |

Витрина и API связаны только адресом API (`API_URL` на сервере витрины),
так что переезд любой половины не трогает вторую. Боевой выкат — обе на
одной машине: так витрина ходит в API по внутренней сети, а API видит
настоящий адрес посетителя. Почему не Vercel — `DECISIONS.md`, решение от
10.09.2026; сам вариант с Vercel описан в `DEPLOY.md` как запасной.

## Проверки на каждый PR

Файл — `.github/workflows/ci.yml`. Порядок такой:

1. **Что затронуто** — по путям определяется, нужна ли проверка витрины,
   API или обеих. Правка README не запускает ничего лишнего.
2. **Витрина** — `npm ci`, линтер, типы, сборка. `npm ci`, а не `install`:
   рассинхрон `package.json` и lock-файла обязан валить сборку, а не молча
   ставить другие версии.
3. **API** — `ruff`, `ruff format --check`, `mypy app`, миграции и тесты на
   настоящем Postgres. SQLite здесь не подошёл бы: схема использует JSONB и
   перечисления Postgres, и тесты на другой базе проверяли бы другой код.
4. **Миграции — в обе стороны**: `upgrade head` → `downgrade base` →
   `upgrade head`. Так ловится ревизия, которая накатывается, но не
   откатывается. Узнать об этом на боевой базе стоит дороже всего.

Повторный пуш в ту же ветку отменяет предыдущий прогон — очередь не
забивается сборками кода, который уже никто не смотрит.

## Выкат на сервер

По тегу `v*` собираются два образа — витрины и API — и публикуются в GHCR
(`.github/workflows/release.yml`). Образы собираются один раз и дальше
только продвигаются по окружениям: пересборка «того же» кода перед
продакшеном означала бы, что в продакшен уезжает не то, что проверяли.

Как поднять их на машине — **`docs/DEPLOY.md`**: подготовка (тег, доступ к
реестру), боевой compose (`docker-compose.prod.yml`), обратный прокси с
сертификатами на два домена, первый администратор, проверка ключа модели,
проверка после выката и честный список того, что осталось незакрытым.

## Окружения

| Окружение | Витрина | API | Когда обновляется |
|---|---|---|---|
| Превью | локально (`npm run dev`) или общий стенд | локально или общий стенд | каждый push в ветку — только проверки |
| Продакшен | образ по тегу `v*` | образ по тегу `v*` | тег |

Превью витрины на Vercel остаётся возможным (`DEPLOY.md`, раздел «Витрина
на Vercel»), но в основной путь не входит.

## Правила ветки `main`

Прямых коммитов нет, только PR с зелёными проверками — см.
`CONTRIBUTING.md`. Защита ветки включается в Settings → Branches
(для приватного репозитория нужен платный план GitHub; на бесплатном
правило соблюдается договорённостью, а не запретом).

## Что нужно включить один раз

**Право `workflow` у токена разработки.** Файлы `.github/workflows` нельзя
пушить токеном без него:

```bash
gh auth refresh -h github.com -s workflow
```
