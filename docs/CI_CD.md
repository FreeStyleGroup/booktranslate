# Сборка и выкат

Устройство рассчитано на несколько команд, работающих параллельно: правка
витрины не должна ждать тестов бэкенда, а выкат одной части — блокировать
другую.

## Что где живёт

| Часть | Где собирается | Где работает |
|---|---|---|
| Витрина `apps/web` | Vercel | Vercel (продакшен + превью на каждую ветку) |
| API `apps/api` | GitHub Actions → образ в GHCR | свой сервер (Docker) |
| База | — | Postgres рядом с API |

Витрина и API разъехались намеренно: Vercel хорош для короткого ответа и
статики, а бэкенду нужны длинные процессы, очередь и постоянное соединение
с базой. Связывает их единственная переменная `NEXT_PUBLIC_API_URL`, так
что переезд любой половины не трогает вторую.

## Проверки на каждый PR

Файл — `docs/ci/github-ci.yml` (переезжает в `.github/workflows/ci.yml`,
см. ниже). Порядок такой:

1. **Что затронуто** — по путям определяется, нужна ли проверка витрины,
   API или обеих. Правка README не запускает ничего лишнего.
2. **Витрина** — `npm ci`, линтер, типы, сборка. `npm ci`, а не `install`:
   рассинхрон `package.json` и lock-файла обязан валить сборку, а не молча
   ставить другие версии.
3. **API** — `ruff`, `ruff format --check`, `mypy app`, миграции и тесты на
   настоящем Postgres. SQLite здесь не подошёл бы: схема использует JSONB и
   перечисления Postgres, и тесты на другой базе проверяли бы другой код.
4. **Миграции — в обе стороны**: `upgrade head` → `downgrade base` →
   `upgrade head`. Так ловится ревизия, которая накатывается, но не
   откатывается. Узнать об этом на боевой базе стоит дороже всего.

Повторный пуш в ту же ветку отменяет предыдущий прогон — очередь не
забивается сборками кода, который уже никто не смотрит.

## Выкат витрины

Автоматический. Push в `main` → продакшен, любая другая ветка → превью со
своей ссылкой, которую можно показать заказчику до слияния.

Root Directory проекта на Vercel — `apps/web`.

⚠️ По умолчанию Vercel закрывает деплои своей авторизацией: посторонний
получает редирект на `vercel.com/sso-api`. Чтобы ссылку можно было
показывать — Project Settings → Deployment Protection → Vercel
Authentication → Disabled для Production.

## Выкат API

По тегу `v*` собирается образ и публикуется в GHCR
(`docs/ci/github-release.yml`). Образ собирается один раз и дальше только
продвигается по окружениям: пересборка «того же» кода перед продакшеном
означала бы, что в продакшен уезжает не то, что проверяли.

Сервер под API ещё не выбран — шаг выката на него добавится, когда
появится машина.

## Окружения

| Окружение | Витрина | API | Когда обновляется |
|---|---|---|---|
| Превью | ссылка на ветку | локально или общий стенд | каждый push в ветку |
| Продакшен | `main` на Vercel | образ по тегу `v*` | слияние в `main` / тег |

## Правила ветки `main`

Прямых коммитов нет, только PR с зелёными проверками — см.
`CONTRIBUTING.md`. Защита ветки включается в Settings → Branches
(для приватного репозитория нужен платный план GitHub; на бесплатном
правило соблюдается договорённостью, а не запретом).

## Что нужно включить один раз

1. **Право `workflow` у токена разработки.** Файлы `.github/workflows`
   нельзя пушить токеном без него, поэтому заготовки лежат в `docs/ci/`:

   ```bash
   gh auth refresh -h github.com -s workflow
   ```

   После этого файлы переносятся в `.github/workflows/` и начинают работать.

2. **Отключить Vercel Authentication** для продакшена — иначе витрину видит
   только владелец аккаунта.
