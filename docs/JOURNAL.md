## 04.09.2026 — этап 3: вход, сессии и контекст организации

**Почему это раньше загрузки документов.** Документ принадлежит проекту, а
проект — организации. Пока запрос не знает, от чьего имени пришёл, приёму
файлов пришлось бы верить на слово тому, что клиент напишет в теле, — и
переделывать это потом вместе со всеми накопленными данными.

**Сделано.**

Регистрация заводит человека и организацию вместе и делает его владельцем:
работать в платформе в одиночку не с чем, а без владельца некому выдавать
права. Короткое имя организации получается транслитерацией названия;
уникальность стережёт ограничение в базе.

Пароли — Argon2id (рекомендация OWASP: в отличие от bcrypt нагружает
память, что обесценивает перебор на видеокартах). Библиотека взята
напрямую, без passlib, который не поддерживается с 2020 года. При каждом
успешном входе проверяется, не пора ли пересчитать хеш под ужесточившиеся
параметры — другого момента, когда пароль известен в открытом виде, нет.

Доступ — короткий JWT (15 минут), обновление — случайная строка со
сроком 30 дней, хранящаяся в базе хешем. Refresh не сделан самодостаточным
намеренно: отозвать подпись нельзя, а запись — можно. При каждом обновлении
токен меняется, старый гасится и помечается, чем заменён. Повторный приход
по уже использованному токену считается кражей: различить его от гонки
клиента невозможно, поэтому гасятся все сессии пользователя.

Организация приходит заголовком `X-Organization-Id`, а не берётся из
токена: человек работает сразу в нескольких и переключается, не выходя из
системы. Если организация не указана, а доступна ровно одна — берётся она;
если несколько — запрос отклоняется, потому что молчаливый выбор означает
запись данных не туда.

Ответы входа не различают «нет такого пользователя», «пароль не тот» и
«учётная запись отключена» — по разнице между ними перебором выясняют,
кто здесь зарегистрирован. Это закреплено тестом.

Ошибки предметной области отделены от HTTP: сервис бросает `AuthError` или
`ConflictError`, обработчик переводит их в коды. Иначе сервис нельзя было
бы вызвать из фоновой задачи, не таща за собой FastAPI.

Одиннадцать тестов: регистрация, повторная почта, вход, неразличимость
отказов, ротация, кража токена, выход, отказ без токена и с испорченным.
Каждый работает в транзакции, которая откатывается.

**Открыто.**

- Приглашение в чужую организацию и смена ролей — сейчас участие
  появляется только при регистрации.
- Восстановление пароля и подтверждение почты.
- Список активных сессий пользователю и кнопка «выйти везде» — данные для
  этого уже пишутся (устройство и адрес).

## 04.09.2026 — этап 2: каркас API, документация, CI/CD

**Сделано.**

Бэкенд `apps/api` на FastAPI: настройки из окружения, асинхронный движок
SQLAlchemy 2 с пулом и `pool_pre_ping`, сессия на запрос, две проверки
живости (`/health` без базы — для перезапуска контейнера, `/health/ready`
с базой — для балансировщика).

Модель данных ядра — организации, пользователи, участие с ролями, проекты,
документы, сегменты. Мультитенантность заложена сразу: `TenantMixin` даёт
обязательную `organization_id` с внешним ключом и индексом. Обоснование
каждого решения — в `docs/DATA_MODEL.md`.

Первая миграция Alembic, окружение миграций берёт адрес базы из настроек
приложения — чтобы он не существовал в двух местах и не разъезжался.
`downgrade` отдельно удаляет перечисления Postgres: они живут независимо от
таблиц, и без этого повторный `upgrade` падал бы на «type already exists».

Локальная среда: `docker-compose.yml` с Postgres и API, код подключён томом,
API стартует только после `healthcheck` базы.

Документация: карта в `docs/README.md`, модель данных, устройство сборки и
выката в `docs/CI_CD.md`, правила работы в `CONTRIBUTING.md`, шаблон PR и
`CODEOWNERS`, этот журнал.

CI: заготовки в `docs/ci/`. Проверки идут по затронутым путям — правка
витрины не гоняет тесты бэкенда. API проверяется на настоящем Postgres,
миграции прогоняются в обе стороны (`up → down → up`): так ловится ревизия,
которая накатывается, но не откатывается.

**Открыто.**

- Право `workflow` у токена: пока его нет, файлы `.github/workflows` не
  пушатся, и заготовки CI лежат в `docs/ci/`. Одна команда —
  `gh auth refresh -h github.com -s workflow`.
- Каркас API написан, но ещё не запускался: Docker Desktop на машине
  разработчика не поднят, а локальный Python — 3.9 против нужного 3.12.
  Первым делом при запуске: `docker compose up --build`, `alembic upgrade
  head`, `ruff format --check .`.
- Vercel Authentication закрывает витрину от всех, кроме владельца аккаунта.

## 04.09.2026 — этап 1: репозиторий и витрина

**Сделано.**

Новый приватный репозиторий `FreeStyleGroup/booktranslate` вместо развития
трёх прежних попыток (`Books`, `BookTranslate-AI`, `BookTranslate-AI-Lab`).
Причины разобраны в `README.md`: мультитенантности нет ни в одной, приём
документов ограничен `.docx` и `.epub`, анализа исходника до перевода нет.
Прежние репозитории остаются донорами кода.

Витрина `apps/web` на Next.js 16 и React 19: лендинг с макетом рабочего
места редактора — сегменты, исходник, перевод, вердикты проверок. Данные
демонстрационные и лежат в самом компоненте; когда появится API, они
заменяются запросом без переделки разметки.

Подключён Vercel: push в `main` уезжает в продакшен, ветки получают превью.

**Открыто.** Стек бэкенда на тот момент выбран не был — решён в тот же
день в пользу Python (см. `docs/DECISIONS.md`).
